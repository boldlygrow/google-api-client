# 5.1

* **Release Date:** 2026-09-07

## Overview

This release adds support for the two credential types that the documentation already recommended but that the package could not actually use: the application default credentials written by `gcloud auth application-default login`, and the service account attached to Google Cloud infrastructure. Developers can now authenticate locally without downloading, storing, or rotating a service account JSON key.

Service account keys continue to work exactly as before and remain the only credential type that supports `subject_email` domain-wide delegation for the Google Workspace APIs.

### New Features

- **`gcloud` application default credentials**
    - Running `gcloud auth application-default login` is now sufficient to authenticate. The package reads `$HOME/.config/gcloud/application_default_credentials.json` (or `%APPDATA%/gcloud/...` on Windows, or `CLOUDSDK_CONFIG` if set) and exchanges the refresh token for an access token.
        - **Why:** The README recommended this as the "recommended method for getting started", but the package only ever supported service account JWT signing, so following the documentation produced a `ConfigurationException`.
- **Attached service accounts**
    - Applications running on Compute Engine, GKE, Cloud Run, or App Engine now authenticate using the attached service account with no configuration. The access token is read from the metadata server and no credentials are stored on disk.
    - `GCE_METADATA_HOST` is honored for proxy and private Google Access setups.
        - **Why:** This was previously documented as a known limitation. It is now implemented and is the preferred method when running on Google Cloud.
- **`GOOGLE_API_KEY_STRING`**
    - The `key_string` connection value can now be set from the environment. It was previously only reachable by passing a connection array to each call, despite being referenced in the documentation.

### What's Changed

- **Credential Resolution**
    - `GOOGLE_APPLICATION_CREDENTIALS` now accepts **either** a path to a JSON key file **or** the JSON key contents. Previously only the contents were accepted.
        - **Why:** Every other Google SDK treats this variable as a filesystem path. Pointing it at a file, which is the documented convention everywhere else, silently failed with an "empty key contents" error.
    - Credentials are dispatched on their `type` field, so `service_account`, `authorized_user`, and `metadata_server` credentials each use the correct grant.
- **Token Caching**
    - Cached tokens now expire based on the `expires_in` value Google returns, minus a 60 second buffer, rather than a hardcoded 3540 seconds.
        - **Why:** Google returns an already-issued token that is partway through its lifetime rather than always minting a fresh one. A token with 10 minutes of life remaining was being cached for 59 minutes, so expired tokens were served for the difference.
- **Error Messages**
    - The `ConfigurationException` for missing credentials now lists every location that was checked and how to fix it, instead of reporting only "The JSON key contents are empty."
    - A base64 encoded `GOOGLE_APPLICATION_CREDENTIALS` value is detected and named as the problem.
    - A JSON key that cannot be parsed reports the JSON error and the source it came from.
    - A service account key missing `client_email`, `private_key`, or `private_key_id` names the missing keys instead of raising an undefined property error.
    - A `private_key` that OpenSSL cannot parse is reported as a configuration error, which most commonly means its newlines were not escaped as `\n`.
    - Requesting a scope that was not consented to during `gcloud auth application-default login` reports the scope and the exact command to grant it.
    - Expired `gcloud` credentials report that reauthentication is needed rather than surfacing Google's `invalid_rapt` string alone.
    - Setting `subject_email` with a credential type that cannot perform domain-wide delegation is rejected with an explanation instead of failing at Google.

### Bug Fixes

- A misconfigured credential value is no longer written into exception messages, logs, or stack traces. A base64 encoded service account key previously had its full encoded private key embedded in the `ConfigurationException` message.
- `ApiClient::logResponse()` accepted `?Carbon` but is called with the result of `now()`. Applications configured with `Date::use(CarbonImmutable::class)` hit a `TypeError` on every successful API call. The parameter is now `?CarbonInterface`.

### Upgrade Steps

- Update `composer.json` to require `boldlygrow/google-api-client:^5.1` and run `composer update`.
- No changes are required. Existing service account configuration continues to work unchanged.
- To authenticate locally without a JSON key, run `gcloud auth application-default login` and remove `GOOGLE_API_KEY_PATH`, `GOOGLE_API_KEY_STRING`, and `GOOGLE_APPLICATION_CREDENTIALS` from your `.env` file.
    - The default scopes granted are `cloud-platform`, `sqlservice.login`, `userinfo.email`, and `openid`. If your application needs another scope, pass every scope it uses to `gcloud auth application-default login --scopes=`.
    - Google Workspace APIs that set `subject_email` still require a service account key with domain-wide delegation.
- Re-publish or update the config file to pick up the `key_string` key: `php artisan vendor:publish --tag=google-api-client`.
- This is not an exhaustive list. Review the `README.md` for the latest syntax and usage guidelines.
